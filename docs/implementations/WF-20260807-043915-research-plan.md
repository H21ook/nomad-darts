## 1. Match State Model

### 1.1 Hierarchy (as documented in `src/types/darts.ts`)

```
Match (MatchState) -> Set (SetType) -> Leg (LegType) -> Turn -> Throw
```

- **Throw** (`darts.ts:33-37`): single dart `{score, multiplier: 1|2|3, segment}`. **Never populated anywhere** — `Turn.throws` is always `[]` (see §6.2). Score entry is per-turn aggregate.
- **Turn** (`darts.ts:40-48`): one visit `{playerId, throws?, points, isBust, dartsUsed, remainingScore, timestamp}`.
- **LegType** (`darts.ts:51-59`): `{id, winnerId, turns[], startScore, dartsToFinish, startTime, startPlayerIndex}`. `dartsToFinish` is **never written** (always 0).
- **SetType** (`darts.ts:62-66`): `{id, winnerId, legs[]}`.
- **MatchState** (`darts.ts:109-126`): the actual persisted shape (see below).
- **Match** (`darts.ts:69-78`): legacy interface (`sets`, `currentSetId`, `currentLegId`, `overallWinnerId`) — **dead code, unused**.
- **Commented-out old MatchState** (`darts.ts:91-100`) — dead code.

### 1.2 MatchState fields (`darts.ts:109-126`, `matchSlice.ts:15-61`)

| Field | Meaning |
|---|---|
| `id` | nanoid; regenerated on `startMatch`/`rematch` |
| `settings` | `{startingScore, firstToSets, firstToLegs, setsEnabled, checkout: 'double'\|'straight', randomOrder}` |
| `active` | `{playerIndex, currentLeg, currentSet}` or `null` (setup/abandoned) |
| `players[]` | `{id, name, score, legsWon, setsWon, order, totalDartsThrown, totalPointsScored, checkoutAttempts, lastThrows, color, image?}` |
| `history.completedSets` | Completed sets (only populated when `setsEnabled` — see §5.3) |
| `status` | `'setup' \| 'playing' \| 'leg_finished' \| 'match_finished'` |
| `lastLegWinnerId` | Winner of the most recent leg (drives LegTransition overlay) |
| `winnerId` | Match winner (drives `/match/finished`) |
| `snapshots` | Undo stack, capped at 20 |

### 1.3 Player fields

- `score` — current leg score (reset to `startingScore` each leg).
- `totalDartsThrown` / `totalPointsScored` — accumulate across the whole match; used for PPR/averages.
- `checkoutAttempts`, `lastThrows` — **declared but never written** (dead fields, see §6.4).
- `order` — 1-based index in `players[]`; `playerIndex` in `active` is the array index.

## 2. Game Rules Implementation

### 2.1 `startMatch` (`matchSlice.ts:67-123`)
1. Stores settings; shuffles players if `randomOrder` (`sort(() => Math.random() - 0.5)` — biased shuffle, not Fisher–Yates).
2. Rebuilds players with fresh stats; `score = startingScore`.
3. `status = 'playing'`, `winnerId = null`, `lastLegWinnerId = null`.
4. Creates first leg/set; `active.playerIndex = 0` (first player in the shuffled array starts leg 1).
5. Clears `history` and `snapshots`.

### 2.2 `submitTurn` — bust & checkout (`matchSlice.ts:125-172`)
- Guard: only when `status === 'playing'` and `active !== null`.
- **Snapshot taken BEFORE mutation** (`takeSnapshotState`, line 131).
- **Bust rule** (lines 139-141): `remaining < 0` **OR** (`remaining === 1 && checkout === 'double'`). Straight-out allows landing on 1.
- Bust turn: `points = 0`, `dartsUsed = 3`, `remainingScore = current score` (unchanged), player's score untouched, `totalDartsThrown += 3`, turn pushed, `nextPlayer`.
- Normal hit: `score -= score`, `totalDartsThrown += dartsUsed`, `totalPointsScored += points`.
- **Checkout**: `remaining === 0` → `handleLegWin` (lines 167-168). **No validation that the final dart was a double** (see §5.1).
- **No input validation**: negative scores, `dartsUsed > 3`, non-finite values are trusted from the UI.

### 2.3 `handleLegWin` (`utils.ts:74-102`)
1. Sets `currentLeg.winnerId`, pushes a deep clone of the leg into `currentSet.legs`.
2. `legsWon += 1`, `lastLegWinnerId = winner`.
3. **Sets disabled**: if `legsWon >= firstToLegs` → `finishMatch` (match over); else `status = 'leg_finished'`.
4. **Sets enabled**: `status = 'leg_finished'`; if `legsWon >= firstToLegs` → `finishSet`.

### 2.4 `finishSet` (`utils.ts:59-72`)
- `setsWon += 1`; `currentSet.winnerId` set; **pushes the completed set into `history.completedSets`**.
- If `setsWon >= firstToSets` → `finishMatch`.

### 2.5 `finishMatch` (`utils.ts:50-57`)
- `status = 'match_finished'`, `winnerId = activePlayer.id`. `active` is left intact (finished leg/set remain readable).

### 2.6 Turning order — `nextPlayer` (`utils.ts:104-107`)
- `(activePlayerIndex + 1) % players.length` — N-player safe.

### 2.7 `startNextLeg` — leg/set alternation (`matchSlice.ts:188-233`)
- Guard: `status === 'leg_finished'` only.
- `isNewSetStarting` = any player `legsWon >= firstToLegs` → reset all `legsWon = 0`, create fresh `currentSet`.
- Starter logic:
  - `setStartPlayerIndex = completedSetsCount % players.length` (set-level alternation).
  - If `currentSet.legs.length === 0` (new set) → starter = `setStartPlayerIndex`.
  - Else → starter = `(setStartPlayerIndex + legsInCurrentSet) % players.length` (leg-level rotation within the set).
- `resetScores`, `status = 'playing'`, `lastLegWinnerId = null`, new leg created with `startPlayerIndex`.
- **Snapshot taken before mutation** (line 192) — undo across leg boundaries works.

### 2.8 `rematch` (`matchSlice.ts:239-294`)
- Keeps `settings`; keeps player ids/names/colors; resets all stats; `status = 'playing'`; clears `winnerId`, `lastLegWinnerId`, `history`, `snapshots`.
- **Starter**: `(previousWinnerIndex + 1) % players.length` — i.e., the **loser** starts the rematch (winner + 1). Falls back to index 0 if `winnerId` not found.

### 2.9 `abandonMatch` (`matchSlice.ts:234-238`)
- `status = 'setup'`, `active = null`, `snapshots = []`. Players/settings/history/winnerId are left stale (harmless — `startMatch` overwrites; `/match` redirects to `/` when `status === 'setup'`).

## 3. Undo Mechanism

- **Snapshot points**: `submitTurn` (before mutation) and `startNextLeg` (before mutation). `rematch`/`abandonMatch`/`startMatch` clear the stack.
- `takeSnapshotState` (`utils.ts:30-48`): deep-clones `players`, `active`, `history.completedSets` via `JSON.parse(JSON.stringify(...))`; stores `status`, `lastLegWinnerId`, `winnerId`. **`state.id` is not snapshotted** (never changes mid-match, so OK).
- **Cap 20**: `if (snapshots.length > 20) snapshots.shift()` (lines 45-47).
- `undo` (`matchSlice.ts:174-187`): pops last snapshot and restores `players`, `active`, `history`, `status`, `lastLegWinnerId`, `winnerId`. One-way (no redo).
- `selectCanUndo` (`matchSlice.ts:300-301`): `snapshots.length > 0`.
- **Undo across leg boundaries**: works — a snapshot taken by `startNextLeg` restores the pre-leg state including `status = 'leg_finished'`, so the LegTransition overlay reappears. Undo from the overlay (LegTransition "Undo last turn") restores the pre-winning-turn state.
- **Undo after match finish**: no UI path (the undo button in `MatchFinished.tsx` is commented out, lines 175-180), but snapshots still exist in state.

## 5. Edge Cases & Potential Bugs

### 5.1 Double Out is not actually enforced (HIGH)
`submitTurn` receives only `{score, dartsUsed}` — no multiplier/segment. Any score landing exactly on 0 wins the leg (`matchSlice.ts:167`). The only double-out enforcement is the "landing on 1 = bust" rule (`matchSlice.ts:141`). `FinishConfirmation.tsx` only asks "how many darts did you use" (1-3), never whether the last dart was a double. A player can "checkout" with a single/triple. README claims "Double Out / Straight Out checkout rules with bust handling" — the bust half is real, the double-out half is cosmetic.

### 5.2 Unfinishable checkout accepted (MEDIUM)
`NumberPad` disables the FINISH shortcut via `checkFinishablePoint` (`utils.ts:10-16`, bogie numbers `[169,168,166,165,163,162,159]`), but a player can type the remaining score manually (e.g., 169) and submit — `handleSubmit` (`NumberPad.tsx:65-68`) opens FinishConfirmation for any `finalScore === currentScore`, and the slice accepts it. `checkFinishablePoint` also ignores the checkout mode (straight-out can finish on 1, but the helper excludes 1).

### 5.3 `history.completedSets` is empty for legs-only matches (MEDIUM)
With `setsEnabled: false`, `handleLegWin` calls `finishMatch` directly and **never pushes the final set to `history.completedSets`** (`utils.ts:88-92`). The comment in `darts.ts:118` ("even without sets, 1 set is stored here") is **false**. All legs of a legs-only match live only in `state.active.currentSet` (which survives `match_finished`). Any future stats/history consumer reading `completedSets` gets nothing for legs-only matches.

### 5.4 Dead stats fields (LOW)
- `Player.checkoutAttempts` — never incremented.
- `Player.lastThrows` — never written.
- `LegType.dartsToFinish` — never written.
- `Turn.throws` — always `[]`; `Throw` type unused in practice.
- `MatchFinished.tsx:157` hardcodes "Checkout 32%"; `:90` hardcodes date "24 OCT 2023"; `:159-162` "Full Statistics" button is a no-op.

### 5.5 dartsUsed is always 3 for non-checkout turns (MEDIUM, stats accuracy)
`NumberPad.tsx:69` submits `onSubmit(finalScore, 3)` for every normal turn; only checkout turns get a real dart count (1-3 via FinishConfirmation). `totalDartsThrown` therefore over-counts, and PPR (`MatchFinished.getAvg`, `MatchFinished.tsx:24`) is inflated for checkout-heavy legs. LegTransition's per-leg average (`LegTransition.tsx:85`) has the same bias.

### 5.6 BUST button is a zero-point turn, not a slice-level bust (LOW)
`NumberPad` BUST → `onSubmit(0, 3)` → slice computes `remaining = score - 0`, which is a bust only when `remaining === 1 && double-out`. Otherwise it records a 0-point, 3-dart turn with `isBust: false`. Scoring outcome is equivalent (score unchanged), but the `isBust` flag and `remainingScore` differ from a true overshoot bust. Edge: at score 1 with double-out, BUST correctly triggers the slice bust.

### 5.7 Rematch starter edge (LOW)
`rematch` starts with `(winnerIndex + 1) % n` (loser starts). If `winnerId` is somehow null at `match_finished` (shouldn't happen), starter = 0. Player order is the previously shuffled order — colors/ids preserved.

### 5.8 Player-count assumptions (MEDIUM, per AGENT.md:8)
The slice itself is N-player safe (`nextPlayer`, alternation modulo). But `MatchFinished.tsx` and score sections assume exactly 2 players per AGENT.md:8; `MatchFinished` renders `players.map` with a VS divider (handles N visually) but only shows the winner's stats. `PlayerList` supports more than 2. If >2 players are enabled, verify all scoring UI.

### 5.9 Stale state after abandon (LOW)
`abandonMatch` leaves `players`, `settings`, `history`, `winnerId` in place; only `status`/`active`/`snapshots` reset. Harmless because `/match` redirects on `status === 'setup'` and `startMatch` rebuilds everything, but the persisted blob keeps stale data until the next `startMatch`.

### 5.10 Persist versioning (MEDIUM)
`version: 1` with no `migrate`. Any future shape change to `MatchState` silently rehydrates stale localStorage. Also `initialState` in `matchSlice.ts` is the fallback only before rehydration.

### 5.11 Misc
- `startMatch` shuffle is biased (`sort(() => Math.random() - 0.5)`).
- `getRandomPlayerColor()` in `initialState` can assign the same color to both players (~10% chance with 10 colors); in practice `MatchSetup` passes explicit `PLAYER_COLORS[0]`/`[1]`.
- `nextPlayer` with `players.length === 0` → modulo-by-zero NaN (unreachable via UI).
- `matchSlice.ts:55` missing semicolon (`state.status = "match_finished"`) — cosmetic.
- `utils.ts:82` commented-out `endTime` line — dead comment.
- `authSlice.selectAccessToken` is typed `(state: AuthState)` not `RootState` — typing smell if used with `useAppSelector` directly.

# T01 — Fix rematch flow

## Task ID and objective

- **Task ID:** T01
- **Objective:** After a match finishes and the user presses PLAY REMATCH, they must land on `/match` (live scoring) with the same settings — not be redirected to `/` (home).

## Implementation summary

The finished page (`src/app/match/finished/page.tsx`) is a **client component** (`"use client"`). It reads Redux state via `useAppSelector` and, when `match.status !== "match_finished"`, calls `redirect('/')`.

When the user presses PLAY REMATCH, `MatchFinished.handleRematch` (`src/components/scoring/MatchFinished.tsx:27`) dispatches `rematch()`, which sets `state.status = "playing"` (`src/lib/redux/matchSlice.ts:263`). The finished page then re-renders, the guard `match.status !== "match_finished"` becomes true, and the page redirected to `/` — the reported bug.

**Fix:** in `src/app/match/finished/page.tsx`, before the generic non-finished guard, add a check: when `match.status === "playing"` (i.e., a rematch was just dispatched), `redirect('/match')` instead of `/`. All other non-finished statuses (`setup`, `leg_finished`) keep the previous `redirect('/')` behavior.

The `/match` page (`src/app/match/page.tsx`) renders the live ScoreBoard for status `"playing"` (it only redirects away for `match_finished` → `/match/finished` and `setup` → `/`), and `rematch()` preserves settings (startingScore, firstToLegs, firstToSets, setsEnabled, checkout, randomOrder), keeps player identities/colors, resets scores/legs/sets/stats, creates a fresh leg+set, and clears history/snapshots — so the rematched match uses the previous settings.

## Changed files

- `src/app/match/finished/page.tsx` (owned file; only file committed)

### Diff

     const match = useAppSelector(state => state.match);

+    // Rematch-ийн дараа шууд амьд тоглолтын дэлгэц рүү буцах
+    if (match.status === "playing") {
+        redirect('/match')
+    }
+
     if (match.status !== "match_finished") {
         redirect('/')
     }
```

## Design decisions

1. **Client component, `redirect()` from `next/navigation`** — the file already uses `redirect()` for its guards, so the fix reuses the same mechanism (Next.js supports `redirect()` in client components during render). No new router hook needed; smallest correct change.

3. **No changes to game logic** — `src/lib/redux/matchSlice.ts` was read-only; `rematch()` already preserves settings and resets state correctly. `src/lib/redux/utils.ts` and `src/types/darts.ts` untouched.
4. **Finished screen still shows results** — the page only redirects when status is not `match_finished`; normal finish flow (status `match_finished`, winner present) renders `MatchFinished` as before. Leaving the finished screen via the AppBar back button (`backHref="/"` in `MatchFinished.tsx:89`) is unchanged.

## Task ID and objective

## Implementation summary

Next.js 16 renamed Middleware to **Proxy**, and the `proxy.ts` file must live at the project root or inside `src/` at the same level as `app` (verified in the bundled docs: `node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md` lines 33–37 — "Create a `proxy.ts` (or `.js`) file in the project root, or inside `src` if applicable, so that it is located at the same level as `pages` or `app`"). ```ts
// src/proxy.ts (new file, committed)
import { updateSession } from "@/lib/supabase/proxy"
import { NextResponse, type NextRequest } from "next/server"

export async function proxy(request: NextRequest) {
    // Guard: if Supabase env vars are missing (e.g. local dev without .env),
    // skip session handling gracefully instead of crashing in createServerClient.
    if (
        !process.env.NEXT_PUBLIC_SUPABASE_URL ||
        !process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
    ) {
        return NextResponse.next()
    }

    return await updateSession(request)
}

export const config = {
    matcher: ["/dashboard/:path*", "/match/:path*"],
}
```

# T04 — Fix client 401-refresh method mismatch

**Status:** Implementation complete, verification passed, committed.
**Workflow:** WF-20260807-043915-research-plan
**Commit:** `fc15f6a` (`fix(auth): align refreshAccessToken method with POST-only refresh route`)

## Objective

`refreshAccessToken` in `src/lib/client-requests/index.ts` issued a **GET** to `/internal/auth/refresh`, but the route only exports **POST** (`src/app/internal/auth/refresh/route.ts:4`), so every call returned 405. Align the method so the refresh path works: returns a token or `null`, preserving the existing deduped `refreshPromise` pattern.

## Approach decision + justification

**Chosen: switch the client to POST, calling `coreFetcher` directly — the route (`src/app/internal/auth/refresh/route.ts`) was NOT modified and remains POST-only.**

Rationale:

1. **POST is the established method for this route.** The server-side caller `src/lib/tokens.ts:45-55` already calls `/internal/auth/refresh` with POST via `serverFetcher.post` → `coreFetcher("POST", ...)`. The route is POST-only; adding a GET handler would needlessly widen the route's surface and duplicate behavior.
2. **HTTP semantics.** The route mutates state (rotates tokens via `setTokens`, `route.ts:29-30`). POST is the correct method for a state-changing operation; GET should be safe/idempotent.
3. **`clientFetcher.post` is intentionally NOT used.** `clientFetcher.post` wraps `withRefresh` (`src/lib/fetcher/clientFetcher.ts:16-37`), whose 401-retry branch calls `refreshAccessToken()` again. Since `refreshAccessToken` is the outermost auth call, a 401 from the refresh endpoint (no refresh cookie → `route.ts:9-14`) would re-enter `refreshAccessToken` while `refreshPromise` is still in flight → circular await on the same promise → permanent hang instead of returning `null`. Using `coreFetcher` directly (no retry layer) matches the server-side pattern (`serverFetcher` calls `coreFetcher` directly) and guarantees the failure path returns `null`.
4. **Minimal diff, zero changes to forbidden files.** Only `src/lib/client-requests/index.ts` changed. `src/lib/fetcher/clientFetcher.ts` and `coreFetcher.ts` are untouched (importing `coreFetcher` is allowed).

## What changed (file:line refs)

**`src/lib/client-requests/index.ts`** (only owned file modified):
- Line 1: import swapped from `@/lib/fetcher/clientFetcher` to `@/lib/fetcher/coreFetcher`.
- Lines 13-16: `clientFetcher.get<RefreshResponse>("/internal/auth/refresh")` → `coreFetcher<RefreshResponse>("POST", "/internal/auth/refresh")` (no body; the route is cookie-based — it reads `getRefreshToken()` from httpOnly cookies and ignores the request body).
- Lines 9-12: comment documenting why POST via coreFetcher (route is POST-only; avoid `withRefresh` recursion).
- Lines 18-22, 24-26: unchanged — `res.isOk` / `res.data.accessToken` / `null`-on-failure and the `refreshPromise` dedupe + `.finally` reset pattern preserved exactly.

**`src/app/internal/auth/refresh/route.ts`**: NOT changed (already POST-only, now consistent with the client).

## Why the bust is dispatched from FinishConfirmation (design decision)

To record a bust without touching NumberPad, the component dispatches `submitTurn` directly. This reuses the T03 `isBust` payload support in `matchSlice.submitTurn` (`explicitBust` → `isBust: true` → points 0, dartsUsed 3, `remainingScore` = unchanged score, `totalDartsThrown += 3`, `playerIndex = nextPlayer`). The dispatch is a separate action from the finish path, but the finish path still flows through NumberPad's `onSubmit` prop as before — no double submission occurs because the two paths are mutually exclusive buttons.
