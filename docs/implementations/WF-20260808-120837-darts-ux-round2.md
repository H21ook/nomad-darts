# Implementation Plan — WF-20260808-120837-darts-ux-round2

## Goal
Fix 3 darts-app issues reported by the user:
1. **Wizard skip + spurious exit dialog + Mongolian dialog text.** After abandoning a match
   mid-game (X → dialog → Гарах), starting Quick Start again lands directly on the players
   page (step 2) instead of step 1; and the exit dialog appears immediately when starting a
   game from the players page. The exit dialog text is Mongolian while the rest of the app
   is English.
2. **Darts row confusion.** The 1/2/3 "Darts used" row under BUST/Bull/FINISH is always
   visible; selecting 2 records a 2-dart turn, but per X01 rules a normal turn is always
   3 darts — only the final checkout turn can be 1/2/3. User asks how to use it.
3. **Button conditions.** FINISH should be inactive on scores where a 3-dart finish is
   impossible (bogies, >170, 1 with double-out). The FINISH shortcut is already disabled,
   but the exact-score entry path bypasses the check, and straight-out mode at score 1 is
   wrongly disabled.

## Architecture
Client-side fixes in Next.js App Router + Redux. No new deps. Root-cause fixes:
- Wizard step tracked in **local state only** (drop URL-driven `?step=2` init) — kills the
  history-residue bug class.
- Remove the **dummy `pushState`/popstate interceptor** in `match/page.tsx` — it desyncs
  Next.js history and is the only non-user path to the exit dialog.
- `ExitConfirmation` translated to English.
- Darts row shown **only when the score is finishable**; normal turns forced to 3 darts.
- `checkFinishablePoint` made **checkout-mode-aware**; exact-score checkout path guarded.

## Tech Stack
Next.js 16 (App Router), React 19, TypeScript, Redux Toolkit, Tailwind CSS v4, framer-motion, shadcn/ui.

# Research Findings — WF-20260808-120837-darts-ux-round2

Date: 2026-08-08 · Investigators: 3× wf-explore (parallel) · Repo HEAD: 1d17dbb (clean tree)

## Issue 1: Wizard skips step 1 after abandon; exit dialog appears on match start; dialog text Mongolian

### Root cause (two coupled defects)
1. **URL-driven wizard step + history residue.** `MatchSetup.tsx:25` initializes step from URL:
   `useState(() => (searchParams.get('step') === '2' ? 2 : 1))`. `handleNext` writes
   `/match/setup?step=2` via `router.replace` (L69) and it is never cleaned up. After abandon,
   history ≈ `[/, /match/setup?step=2, /match, /]` — the `?step=2` entry survives. Any
   back/forward (hardware back on PWA, browser back, Next.js history reconciliation) lands on
   `/match/setup?step=2` → wizard renders step 2 (players page) directly. The previous fix
   (9d488ed) replaced the `#order` hash hack with `?step=2` but did NOT remove the history
   residue — same failure mode, new URL scheme.
2. **Match page popstate interceptor desyncs Next.js history.** `match/page.tsx:27-40` pushes
   manual dummy entries (`window.history.pushState({match:true},'')`) on mount and on every
   popstate. This desyncs Next.js App Router's internal history index. When Next.js later
   navigates (e.g., `router.push('/match')` from START MATCH), it may reconcile via
   `history.go()` → fires `popstate` → the freshly mounted listener opens the exit dialog
   immediately after starting a game. This is the ONLY non-user path to `showExitDialog`.

### Language inconsistency
- `ExitConfirmation.tsx` is 100% Mongolian ("Тоглоомоос гарах уу?", "Одоогийн тоглоомын явц
  устагдана.", "Үргэлжлүүлэх", "Гарах") — the ONLY user-facing Mongolian text in the app
  (verified by grepping JSX text nodes for Cyrillic). All other UI (landing, setup wizard,
  scoring, stats) is English. User wants the dialog in English to match.

### Facts
- `abandonMatch` (matchSlice.ts:229-233) sets status "setup", clears active/snapshots, keeps players — fine.
- `startMatch` overwrites everything — no stale-player leakage.
- Landing "Resume Match" card only shows when status === 'playing' — not the culprit.
- Wizard players come from local state only (MatchSetup.tsx:27) — no Redux pre-fill.
- Previous workflow's verification was code-tracing + build only; the manual browser walkthrough
  was never actually executed (docs/implementations/...:284-306).

### Recommended fixes
- **A (wizard):** stop trusting the URL for step initialization. Track step in local state only;
  remove `router.replace('/match/setup?step=2')` / `router.replace('/match/setup')` calls
  (or keep URL purely cosmetic). Simplest: local state only — kills the whole bug class.
- **B (match page):** remove the dummy `pushState`/popstate interceptor (or make it
  Next.js-safe). The X button in the AppBar already opens the exit dialog; hardware back
  without the interceptor leaves the match (persisted, resumable via Resume card).
- **C (localization):** translate ExitConfirmation.tsx to English ("Exit game?",
  "Current match progress will be lost.", "Continue", "Exit").

## Issue 2: Darts row (1/2/3 selector) under BUST/Bull/Finish

### Current behavior
- `NumberPad.tsx:21` `const [dartsUsed, setDartsUsed] = useState(3)`; row at lines 156-177,
  ALWAYS visible, label "Darts used" (renamed from "Darts" in 9d488ed).
- Selecting 2 means "this turn used 2 darts" → `onSubmit(score, 2)` → `totalDartsThrown += 2`
  (matchSlice.ts:158) → affects PPR / avg darts per leg.
- BUST forces 3 darts (NumberPad.tsx:64-70, matchSlice.ts:143,151).
- FINISH shortcut (NumberPad.tsx:44-50) submits directly with the row's dartsUsed, skipping the
  FinishConfirmation dialog.
- Exact-score entry path opens FinishConfirmation dialog which RE-ASKS darts count (1/2/3)
  and overrides the row selection (NumberPad.tsx:89-94, FinishConfirmation.tsx:56-70).
- Reducer accepts any dartsUsed (default 0 if omitted); tests cover 1/2/3.

### User's question
"How is the Darts row used? If I select 2, it means I've already thrown 2 darts. Per the rules,
a 2-dart turn shouldn't happen, right?" — The user is confused because the row is always visible
and applies to ALL turns, but per X01 rules a normal turn is always 3 darts; only the FINAL
(checkout) turn can legitimately be 1, 2, or 3 darts. The row is meant for the final turn.

### Fix direction
- Show the Darts row ONLY when the current score is finishable (checkout situation) — i.e.,
  when `canFinish` is true. For non-finishable scores the row is hidden and dartsUsed stays 3.
  This directly answers the user's question: the row is for the final turn where you can finish
  with 1, 2, or 3 darts.
- Keep label "Darts used" (or clarify to "Darts used to finish" when shown).

## Issue 3: Button conditions — Finish disabled when 3-dart finish impossible

### Current state
- `checkFinishablePoint` (utils.ts:8-16): `score <= 170 && score >= 2 && !bogieNumbers.includes(score)`
  with bogies = [169, 168, 166, 165, 163, 162, 159]. Mathematically correct for double-out.
- FINISH button already has `disabled={!canFinish}` (NumberPad.tsx:143) + pointer guard (144) +
  dimmed style (147). So the FINISH shortcut IS already disabled for bogie scores.
- **Gap 1 (bypass):** the exact-score entry path is UNGUARDED. User types the current score
  (e.g., 169) → Check button (disabled={!value} only) → `handleSubmit` → `finalScore ===
  currentScore` → FinishConfirmation opens → confirm → leg win. A non-finishable score can
  still be finished this way.
- **Gap 2 (mode):** `checkFinishablePoint` ignores checkout mode. In straight-checkout mode,
  score 1 IS finishable (single 1), but the function returns false → FINISH incorrectly
  disabled at 1 in straight mode.
- **Gap 3 (optional):** dartsUsed feasibility (e.g., 170 with 1 dart selected is impossible) —
  not requested; defer.

### Fix direction
- Make `checkFinishablePoint` mode-aware: accept checkout mode ('double' | 'straight'); allow
  score 1 in straight mode.
- Guard the exact-score/FinishConfirmation path: block opening the dialog (and submission)
  when `!checkFinishablePoint(currentScore, checkout)`.
- Extend `utils.test.ts` for straight-mode score 1.
